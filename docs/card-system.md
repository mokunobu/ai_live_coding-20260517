# Obsidian Information System

## 目的

情報を蓄えるだけでなく、後から調査、設計、実装、レビュー、報告に使える状態で管理する。

このルールの目的は、情報量を増やすことではない。別スレッドや別作業者が、同じ元ネタ、判断、検証、次の作業へ戻れるようにすること。

## 基本方針

- Zettelkasten + MOCで扱う。
- 1出典、1情報、1知識、1作業判断を1カードにする。
- Zettelkastenの中心は「保管」ではなく「後で組み合わせられる原子化した知識」を作ること。
- フォルダは少数の役割フォルダに限定する。
- テーマ別、DIKW別、案件別に深いフォルダを作らない。
- 意味分類はfrontmatter、タグ、リンク、MOCで扱う。
- カードIDと元ネタだけを安定させる。
- MOCは結論ではなく、使うための地図として扱う。

## Zettelkasten分解ルール

このVaultでは、Zettelkastenを次の対応で運用する。

| Zettelkasten上の役割 | このVaultでの扱い | 目的 |
| --- | --- | --- |
| Fleeting note | `inbox/`, 必要に応じて `WRK` | その場の断片。正式な根拠にしない |
| Source note | `SRC` | 元ネタの所在、取得日時、証跡を残す |
| Literature note | `INF` | 元ネタから、使える可能性のある情報を抽出する |
| Permanent note | `KNW` | 自分の言葉で、再利用できる1つの知識にする |
| Index / Structure note | `MOC`, `use-moc.md` | 目的別にカードをたどる地図を作る |

### 原子化の基準

`KNW` は、原則として「1カード = 1つの主張、判断基準、手順、失敗条件、使い方」にする。

分ける条件:

- その知識だけを別の作業で再利用できる。
- 根拠となるSRC / INFが異なる。
- 採用条件、失敗条件、使わない運用が異なる。
- AIへの指示、レビュー質問、実装ルールとして別々に使える。
- 1枚のカード内に `そして`, `また`, `一方で`, `ただし` が増え、別の論点が混ざっている。

分けない条件:

- その説明がないと1つの主張として理解できない。
- 出典の所在、取得日時、証跡のように、同じSRCで管理すべきメタ情報である。
- まだ抽出段階で、再利用できる判断基準になっていない。この場合は `INF` または `WRK` に留める。

### KNWへ昇格する条件

`INF` から `KNW` へ移すのは、次を満たしたときだけにする。

- 元ネタではなく、自分の言葉で言い換えられている。
- どの場面で使うかが書ける。
- どの場面では使わないかが書ける。
- 成功条件または失敗条件が書ける。
- 少なくとも1つのSRC / INFへ戻れる。

満たさない場合は、無理に `KNW` にせず `status: needs-resolution` または `status: needs-evidence` として残す。

### リンクルール

原子化した `KNW` は、孤立させない。

- `source`: 根拠になるSRC / INF。
- `supports`: 支えるカード。
- `contradicts`: 反対または注意が必要なカード。
- `applies_to`: 使う作業、ページ、成果物。
- `used_by`: 実際に使ったWRKや成果物。

リンクが張れないカードは、使い道が未整理の可能性が高い。削除せず、`要確認` に「どのMOCへ接続するか」を書く。

### デザイン知識の分解例

デザイン情報は、ギャラリーや記事を集めるだけでは `KNW` にしない。

例:

- `SRC`: MUUUUU.ORGの掲載基準ページ。
- `INF`: 掲載基準では、レイアウト整合性、情報階層、導線、コンテンツとビジュアルのバランスを見ている。
- `KNW`: 余白は装飾ではなく情報のまとまりを示す。
- `KNW`: 視覚階層は、訪問者に読ませる順番を決める。
- `KNW`: コントラストは雰囲気より可読性を優先する。
- `KNW`: KLGでは木のモチーフを装飾ではなく、知識の成長構造として使う。
- `MOC`: 会社HPデザイン時に使う判断カードの入口。

「良いサイトまとめ」「AIっぽくないサイトまとめ」のような大きなカードは、MOCまたはINFに留める。実制作で使う前に、必ず小さな `KNW` へ分解する。

## フォルダルール

採用するフォルダは次に限定する。

```text
docs/
  00-index.md
  card-system.md
  card-template.md
  source-moc.md
  info-moc.md
  knowledge-moc.md
  work-moc.md
  use-moc.md
  sources/
  info/
  knowledge/
  work/
  files/
  evidence/
  templates/
  inbox/
```

### 作らないフォルダ

- `data/`, `information/`, `wisdom/` のようなDIKW固定フォルダ。
- `marketing/`, `design/`, `ai/`, `reels/`, `lp/` のようなテーマ固定フォルダ。
- `important/`, `archive-needed/`, `maybe/` のような状態だけを示す曖昧なフォルダ。

テーマ、重要度、状態はタグやfrontmatterで管理する。

## DIKW対応

DIKWはフォルダではなく、カードの役割として扱う。

| DIKW | このVaultでの扱い | 主な場所 |
| --- | --- | --- |
| Data | 元ネタ、原本、証拠 | `files/`, `evidence/`, `sources/` |
| Information | 元ネタから抽出した使える情報 | `info/` |
| Knowledge | 再利用できる判断基準、手順、型 | `knowledge/` |
| Wisdom | いつ何を使うかの判断地図 | `use-moc.md`, `work/` |

`Work` はDIKWの前後にある作業層として扱う。Rawではなく、調査、比較、採否判断、検証、成果物管理の記録である。

## 適用範囲タグルール

`SRC / INF / KNW / WRK / MOC` は、情報処理の段階を示す分類である。

それとは別に、`KNW` には原則として「その知識がどこまで使えるか」を示す `scope` タグを1つ付ける。

| タグ | 意味 | 例 |
| --- | --- | --- |
| `scope/global` | KLGや特定案件に限らず、広く再利用できる知識 | 余白、視覚階層、可読性、Zettelkasten原子化 |
| `scope/domain` | 特定領域では使えるが、会社固有ではない知識 | B2B、AI/DX、研修、カンパニーサイト、Webデザイン |
| `scope/local` | KLG固有、または今回案件固有の知識 | KLGの社名思想、ロゴ、今回の会社HP刷新判断 |

詳細な領域は追加タグで表す。

```yaml
tags:
  - scope/domain
  - domain/b2b
  - domain/ai-dx
```

```yaml
tags:
  - scope/local
  - local/klg
```

### scopeの判断

- カードの中心主張が汎用なら `scope/global`。
- カードの中心主張がB2B、AI/DX、研修、Web制作などの領域に依存するなら `scope/domain`。
- カードの中心主張がKLG、今回の会社HP、ユーザー固有事情に依存するなら `scope/local`。

汎用カードにKLGへの適用例を書くことはできる。ただし、KLGへの適用が中心主張になる場合は、別の `scope/local` カードへ分ける。

## Stitch / DESIGN.md運用ルール

Stitchはデザイン生成とデザインシステム作成の作業ツールであり、元ネタそのものではない。

### 接続確認

- Stitch MCPで `create_project` などの基本操作が成功する場合、MCP接続は生きていると判断する。
- 個別RPCが `invalid argument` などで失敗しただけでは、すぐに繋ぎ直しと判断しない。
- 繋ぎ直しを検討するのは、Stitchツールが一覧に出ない、全RPCが無反応、認証/権限エラーが継続する、Stitch UI側に作成結果が反映されない場合に限る。

### DESIGN.mdの正本

- ルート `DESIGN.md` を正本にする。
- `docs/files/` と `docs/work/` に置くDESIGN.md相当の内容は、Stitch投入用の派生、コピー、または作業記録として扱う。
- `DESIGN.md` は、`KNW` の判断カードをAI実装/Stitch用ブリーフへ変換した作業成果物として扱う。
- `DESIGN.md` は雰囲気メモにしない。tokens、components、layout、responsive、accessibility、do/don't、agent prompt、review checklistを最低要件にする。
- 外部の `DESIGN.md` 集やテンプレートは、直接流用せず、まず `SRC` に元ネタを残し、`INF` で抽出し、必要なルールだけ `KNW` へ分解する。
- 品質確認は [[knowledge/KNW-016-DESIGN-md品質ゲート|KNW-016 DESIGN.md品質ゲート]] に従う。

### デザインシステム作成手順

Stitchでデザインシステムを作る場合は、原則として次の順に進める。

1. `KNW` から必要な判断カードを選ぶ。
2. ルート `DESIGN.md` を確認する。
3. Stitchプロジェクトを作成または確認する。
4. `upload_design_md` でルート `DESIGN.md` をアップロードする。
5. `create_design_system_from_design_md` でデザインシステム化する。

`create_design_system` の直接作成ルートが失敗した場合は、接続障害と決めつけず、`upload_design_md -> create_design_system_from_design_md` の正規ルートへ切り替える。

### Stitch出力の取得

Stitch出力は、原則としてStitch MCP経由でCodexが直接取得する。

1. `get_project` でプロジェクト状態を確認する。
2. `list_screens` で画面一覧を取得する。
3. `get_screen` で対象画面の詳細を取得する。
4. 取得結果、画面ID、判断、未確認事項を `WRK` に記録する。
5. Stitch出力を後続作業の元ネタとして扱う場合だけ、対応する `SRC` を作る。

URL、スクリーンショット、エクスポートは、MCP直接取得ができない場合や視覚確認が必要な場合のフォールバックまたは補助証跡として扱う。

### 使わない運用

- Stitchに渡したプロンプトやDESIGN.mdを、元ネタ扱いしない。
- Stitch出力を、検証なしに会社HPの正式デザイン判断にしない。
- AIが作った色、余白、CTA、コピー、構成を、対応する `KNW` へ戻さず採用しない。
- Stitch MCPで取得できる画面情報を、最初から手作業のURL/スクリーンショット取得だけに頼らない。

## カード種別

### SRC

出典カード。元ネタの所在、取得元、確認日、注意点を管理する。

- 置き場: `docs/sources/`
- ファイル名: `SRC-001-日本語タイトル.md`
- 元ネタ本文を丸コピーしない。
- どこを見れば原本や証跡に戻れるかを明記する。
- 事実、解釈、使用候補を混ぜない。

### INF

情報カード。元ネタから抽出した、使える可能性のある情報を管理する。

- 置き場: `docs/info/`
- ファイル名: `INF-001-日本語タイトル.md`
- 採用、不採用、IA位置、優先度をここで固定しない。
- 必ず参照元SRCへ戻れるようにする。

### KNW

ナレッジカード。再利用できる判断基準、手順、テンプレート、失敗条件を管理する。

- 置き場: `docs/knowledge/`
- ファイル名: `KNW-001-日本語タイトル.md`
- 案件固有の事実根拠として使わない。
- 適用範囲、再現手順、完了条件、禁止運用を書く。
- 1枚に複数の独立した知識を入れない。
- `INF` の要約をそのまま `KNW` にしない。自分の言葉で再利用可能な判断に変換する。
- 抽象論だけで終わらせず、採用条件、不採用条件、失敗条件、レビュー質問を書く。
- `scope/global`, `scope/domain`, `scope/local` のいずれかを付け、知識の適用範囲を切り離せるようにする。

### WRK

作業カード。調査、比較、設計、検証、成果物管理、判断ログを管理する。

- 置き場: `docs/work/`
- ファイル名: `WRK-001-日本語タイトル.md`
- 元ネタではない。
- 入力、手順、判断、成果物、検証、未完了事項を書く。

## MOCルール

MOCはカードを探すための地図であり、カード本文や結論の代替ではない。

- `source-moc.md`: 出典カードの入口。
- `info-moc.md`: 抽出情報カードの入口。
- `knowledge-moc.md`: 再利用ナレッジの入口。
- `work-moc.md`: 作業記録の入口。
- `use-moc.md`: 作業目的別に、どのSRC / INF / KNW / WRKを見るかを示す入口。

新しいカードを作ったら、該当MOCへリンクを追加する。

## タイムスタンプルール

ファイルシステムの `ctime` / `mtime` は、Git checkout、コピー、同期、復元で変わるため、記録の根拠にしない。

Markdownのfrontmatterに、次のタイムスタンプを明示する。

```yaml
created: 2026-05-17
updated: 2026-05-17
source_observed_at:
evidence_captured_at:
```

### 必須項目

- `created`: カードを作成した日。全カード必須。
- `updated`: 内容を実質更新した日。全カード必須。
- `source_observed_at`: 元ネタを確認した日時。SRCでは原則必須。
- `evidence_captured_at`: スクリーンショット、HTML、ログなどを保存した日時。証跡がある場合は必須。

### 日時形式

- 日付だけで十分な場合: `YYYY-MM-DD`
- 時刻が判断に影響する場合: `YYYY-MM-DD HH:mm JST`
- 外部ページ、SNS、価格、規約、仕様、API、ニュースなど変わる情報は、時刻まで残す。

## 保存前品質ゲート

カードを保存、更新、利用する前に、次を確認する。

- 何のために残すかが書かれている。
- 1カード1論点になっている。複数論点なら分割先が書かれている。
- 元ネタ、URL、ファイル、スクリーンショット、ログの所在がある。
- 確認済み事実と私の解釈が分かれている。
- 再現手順がある。
- 検証方法、完了条件、失敗条件がある。
- 使ってよい範囲と、使ってはいけない範囲がある。
- 作成日、更新日、必要な確認日時がある。
- MOCまたは関連カードへ接続されている。

不足している場合は、削除せず、`status: needs-resolution` または `status: needs-evidence` として不足項目を明記する。

## 情報分類ルール

カード本文では、必要に応じて次の見出しを分ける。

- `元ネタ`: ユーザー発言、出典文、ファイル、スクリーンショット、ログ。
- `確認済み事実`: 証拠から直接確認できること。
- `私の解釈`: 分類、仮説、意味づけ、要約、使い方の判断。
- `使用候補`: どの作業、資料、成果物で使えるか。
- `要確認`: 追加確認が必要なこと。
- `使わない運用`: 誤用、禁止表現、未確認のまま使ってはいけない条件。

整理文書、過去成果物、AI要約、既存カードは、元ネタそのものではない。必要なら関連資料として扱う。

## ファイルと証跡

### files

`files/` は元ファイル、受領素材、PDF、画像、動画、外部から保存した資料を置く。

- ファイルを置いたら、対応するSRCかWRKから参照する。
- `files/` 内の素材を成果物から直接参照しない。
- 加工、採用、公開利用する場合は、WRKで判断と使用範囲を記録する。

### evidence

`evidence/` は証跡を置く。

- スクリーンショット
- 保存HTML
- コマンドログ
- 検証出力
- 比較画像
- レポート生成物

証跡を置くだけで完了にしない。何が写っていれば証拠成立か、どの判断に使うかをカードに書く。

## Inboxルール

`inbox/` は未整理の一時置き場。

- 一時メモ、未分類URL、受領直後の断片を置いてよい。
- 正式な判断、設計、成果物に使う前に、SRC / INF / KNW / WRKへ変換する。
- `inbox/` のまま下流作業の根拠にしない。

## 変更ルール

情報整理やルール変更を行う前に、チャット上で次を示す。

- 変更対象
- 変更理由
- 影響範囲
- 変更前後の差分
- 戻し方

変更後は、次をチャットで要約する。

- 変更したファイル
- 追加または変更した情報カテゴリ
- 確認済み事実と私の解釈の分離
- 未確認事項
- 次に見るべき場所
